# 記事改善の編集・反映手順

I-0007の投稿318対応で確認した手順。実施記録はD-0018、教訓はL-0009。
本書はAIへの本番更新権限の付与や、今後の記事更新の包括承認ではない。

## 原稿の作成

1. 最新の記事本文と保存場所を確認し、読者・目的・変更理由を整理する。事実の訂正と編集方針の変更を分ける。
2. 元記事の構成・語り口・意図を保持する。関連箇所の矛盾解消に必要な範囲で直し、文脈上不要な説明や社内運用ルールを追加しない。大幅変更が必要なら理由と範囲を提示する。
3. 「本記事のポイント」は記事を読むと理解できる内容を各100文字以内にまとめる。HTMLタグを除き句読点・英数字を含む表示文字数を確認する。
4. strong、リンク、番号付きリスト、箇条書き、コード、画像、目次とアンカーを保持する。タイトル・URL・SEOメタは承認された変更対象だけ扱う。
5. 公式情報と照合し参照日を残す。新規節は既存テーマのクラスを確認して作り、CSS追加の要否を判断する。
6. 改行形式を入力時に確認する。CRCRLF等の変換で空行を増やさず、pre/code内の改行を保持する。無関係な本文の一括整形を避ける。

## レビューと反映

- 変更前後の比較と、修正を組み込んだ記事全体のプレビューを用意する。確認用装飾や操作ボタンを貼り付け用本文へ混ぜない。
- 最終本文を明示し、修正後にプレビューも同期する。古い原稿は採用版として案内しない。
- Developmentのドメイン・投稿ID・slugを確認する。環境間でIDが同じと決めつけない。
- 変更前本文を退避し、承認済み範囲だけ貼り付けて実テーマで確認する。テーマのPRやデプロイだけではWordPress本文は更新されない。
- リンクの遷移先・参照目的・リンクと分かる装飾を確認する。別タブが承認されたリンクには `target="_blank"` と `rel="noopener noreferrer"` を付ける。
- D-0005に従いPC・スマートフォン表示・操作性・既存機能への影響・Consoleを確認し、未確認は明記する。プレビュー確認と保存後確認を区別する。
- Productionは別途Humanの明示承認を得る。最新の本番本文を保存してDevelopmentの修正と差分照合し、対象記事だけ更新する。DB全体同期は行わない。
- 保存後は公開URLで本文・装飾・目次・リンク・環境URL混入を確認し、公開日、確認者、確認範囲、未検証事項を記録する。
- 復旧が必要なら現在の本文も退避し、承認範囲を確認して変更前本文を対象記事へ戻す。バックアップの存在と復元テスト済みは区別する。
- 操作をHumanに依頼する場合は1ステップずつ案内する。

## 効果測定

対象URL、施策、公開日、比較期間、クリック・表示回数・CTR・平均掲載順位を残す。
公開後28日間など比較窓を決め、データ確定遅延を考慮して取得する。少数データ・検索需要・他施策の影響があるため、前後比較のみで因果効果を断定しない。
記録の作成だけで定期測定や通知を設定したとはみなさない。

- 200応答でも内容が参照目的と異なる場合がある。公式の移転先と内容を照合する。
- 最初は検知・記録・修正案生成を対象とし、置換はHuman承認後にDevelopmentで検証し、本番は別途承認する案を検討する。

実パスは未決定。既存の「親ディレクトリが書き込み可能」という判定では採用せず、公開領域外であること、所有者・アクセス権、容量、シンボリックリンクやパストラバーサル対策を確認する。ディレクトリ700・ファイル600を基本案とし、既存ファイルを上書きしない。保持は30日を初期案とするが、期間はHuman判断。復元検証済みになるまで削除せず、自動削除は別途設計・承認する。

1. **実装前レビュー**：対象Development・操作対象記事・保存先・保持期間・実行主体・アクセス制限を確定する。既存SSH鍵の権限範囲は未確認であり、Devin等へ直接渡さない。固定操作だけを許す実行経路を設計し、書き込みPoC前にレビューする。
2. **バックアップだけのPoC**：投稿318の環境、type、slug、状態を再照合。本文を加工せず保存し、環境識別、投稿ID、取得時刻、本文バイト数・SHA256、実行ID、形式版数を管理情報に残す。タイトル・slug・状態・SEO等は変更対象外として比較用に確認する。DB全体や認証情報は含めない。保存データを読み戻し、サイズ・SHA256一致を確認。ログには本文を出さない。ここでは記事更新しない。
3. **隔離した復元試験**：初回は非公開のテスト用投稿または隔離環境で、退避→試験変更→復元→一致確認を行う。テスト投稿の作成も別途承認対象。投稿318を故意に壊して復元試験しない。HTML、strong、改行、pre/code、目次、リンク等の保存後一致と実表示を検証する。
4. **対象記事の更新PoC**：復元試験合格後、承認済み本文のハッシュ・対象記事・変更範囲を固定。直前に新たなバックアップを作り、現在本文が承認時の元本文と一致する場合だけ更新する。他の編集があれば停止し、再比較する。テーマデプロイ・他のActions・管理画面編集との競合を扱う。Actionsのconcurrencyだけでは管理画面編集を防げないため、ハッシュ確認と更新間の競合も防ぐ仕組みを実装前に決める。
5. **保存後検証と復元判断**：保存された本文を再取得し、承認本文との一致、対象外項目の維持、PC/SP・装飾・目次・リンク・環境URL混入を確認。不一致なら追加更新を止める。復元時も現在本文を退避し、別の編集がないことと復元対象・バックアップの一致を確認する。失敗時の自動復元は初期PoCに含めず、Human承認を受けて実施する。

### 保存先・実行権限の具体案（2026-10-28、調査・設計段階）

HumanはDevelopment内の非公開保存先、原則30日・復元検証まで保持、自動削除なし、投稿318のバックアップだけを行う方針の調査・実装案作成を承認。フォルダ作成、鍵発行、権限変更、バックアップ実行はまだ承認・実施していない。

**保存先候補**：検証済みのDevelopment WordPressルートの親にある `private-article-backups/post-318/`。絶対パスは公開文書へ記載しない。これは論理的な候補であり、未作成・未検証。既存probeの親ディレクトリ書込み可判定だけでは、非公開領域と断定できない。

実装前の読み取り調査では、対象WordPressルートの末尾がpublic_htmlか、親の実体・所有者・アクセス権・空き容量、候補の既存有無とシンボリックリンク有無を確認する。他ドメインからの公開設定やWebサーバーのaliasまではファイル位置だけで判断できない。サーバーパネル情報等で公開範囲を確認し、確認不能なら保存先を採用しない。公開可否を確かめるために本文を置くことはしない。確認用ファイルの作成・HTTP照合が必要なら別途承認する。

**権限の現状**：既存Actionsはdevelopment EnvironmentのSSH鍵を使い、リモートでbashを実行する。投稿318限定はスクリプトの検査であり、OS・SSH鍵の権限を318へ限定した証拠ではない。READ ONLYトランザクションもDBユーザー自体の権限縮小ではない。前段の提案でいう「記事更新・復元権限を付けない」は今後の専用実行経路の目標であり、現状を保証する表現として使わない。

**推奨候補**：バックアップ専用鍵から、サーバー側に配置した固定の処理だけを起動する。OpenSSHのforced commandと転送・PTY等の禁止を組み合わせ、通常シェル、任意コマンド、SFTP、任意パス・投稿ID・SQL・コードの入力を許さない。現在のようにクライアントからPHPコードを渡して実行する方式は専用鍵では採用しない。サーバー側処理がDevelopment・投稿318を再照合し、固定保存先だけへ新規保存、読戻し検証を行い、本文を返さず結果だけを返す。更新・復元・削除の操作は実装しない。

ただしforced commandはOSユーザーの分離ではない。同じOSユーザーの別経路から処理ファイルや認証設定を書き換えられるリスクが残る。既存デプロイ鍵をExecutorへ渡さず、処理ファイルをテーマと分離し、変更経路を管理する。厳密なOS/DB権限分離が必要なら独立したユーザー・実行環境等を選ぶ。Xserverの現契約でforced command設定の保持・利用や独立ユーザーが可能かは未確認であり、できると断定しない。

代替は既存SSH鍵とレビュー済みスクリプトを利用する方式。導入作業は少ないが鍵自体の権限が広いままで、今回目指す専用経路の制限には届かないため初期推奨にしない。専用実行経路が利用できない場合は、制限を省いて続行せず、環境分離または手動バックアップを選び直す。

**保存処理の実装要件**：新規フォルダ700・ファイル600、既存パス・リンクの上書き禁止、排他的作成、本文バイト列と管理情報を一組で扱う。途中失敗を成功扱いしない。本文64,382 bytesは過去の観測値であり固定上限や期待値にしない。実行ごとに新規取得したサイズ・SHA256で照合する。管理情報に本文・DB資格情報を混ぜず、ログへ絶対パスを出さない。保持期限は作成時刻とともに記録するが自動削除しない。

**次のレビュー単位**：
1. 保存先候補の読み取り調査コードを作成・ローカル検証してPR化する。サーバーでの実行は別途承認し、フォルダ・鍵・権限を変更しない。結果は存在・所有者一致・公開ルート外判定等の固定フラグと容量だけに限定する。
2. Xserverでの専用鍵制限の適用方法・維持条件を確認する。未確認の場合はHumanへ確認箇所を1ステップずつ案内する。秘密鍵やauthorized_keys全体の提出を求めない。
3. 読み取り結果と専用経路の可否がそろってから、実パス・変更対象・切戻し方法・鍵の保存先・制限検証方法を提示し、セットアップ承認を受ける。既存デプロイ鍵の設定は流用変更しない。
4. 専用鍵で任意操作が拒否されること、対象外のパスや記事IDを受け付けないことを検証後、バックアップ1回の実行を別途承認する。Productionを操作して制限を試すことはしない。
